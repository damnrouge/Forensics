Prerequisites – What You Need to Know First

To fully understand this topic, you should already know:

LSASS & Credential Storage ▼
Local Security Authority Subsystem Service holds authentication data for active logon sessions (NTLM hashes, Kerberos tickets, sometimes plaintext). It is the primary target of MITRE T1003.001.
Protected Process Light (PPL) ▼
PPL is a Windows protection that prevents lower-privilege processes from opening handles with dangerous rights (VM_READ, etc.) to higher-protected processes. LSASS often runs as PPL (especially with RunAsPPL enabled). Only equal or higher PPL levels (e.g. WinTCB) can interact freely.
MiniDump & MiniDumpWriteDump ▼
A MiniDump is a structured snapshot of a process’s memory. The Windows API MiniDumpWriteDump (from dbghelp/dbgcore) is the standard way tools create these dumps. Almost every LSASS dump technique eventually calls it or an equivalent.
Basic EDR Telemetry ▼
You should be comfortable with Sysmon Event ID 1 (process create), 10 (process access), 11 (file create), Windows Security 4688, and the idea that “WerFault touching LSASS” is often treated as benign by default.

If any of these feel fuzzy, expand the cards above and make sure the mental model is solid before continuing. Everything else builds on them.

Simple Explanation (Feynman)

Imagine Windows has a “crash photographer.” When a program crashes, this photographer (WerFault) takes a detailed photo of the program’s memory so Microsoft can later figure out what went wrong. Attackers discovered they can whisper to the photographer “Hey, LSASS just had a problem” even when LSASS is perfectly healthy. The photographer then takes a full photo of LSASS’s memory and saves it to disk — exactly the photo an attacker needs to steal passwords.

Where people usually get confused

  • • Thinking the technique requires actually crashing LSASS (it doesn’t).
  • • Believing PPL makes dumping impossible (it only raises the bar on who can dump).
  • • Assuming every WerFault access to LSASS is malicious (most are not — context is everything).
  • • Forgetting that the final dump file is the real prize; process events are just the trail.

1. Why LSASS Is the Prize

Simple Explanation

When you log on to Windows, the system needs to remember “who you are” so it can keep granting you access to files, network shares, and other machines. That memory lives inside the LSASS process. If an attacker can take a complete snapshot of that process’s memory, they can later extract the password hashes (and sometimes clear-text passwords) offline and use them for lateral movement — exactly like stealing the master keyring of a building.

Analogy

LSASS is the hotel’s front-desk computer that keeps every guest’s keycard data in RAM. Dumping it is photocopying the entire keycard database while the clerk is looking the other way.

Why it works this way

Windows needs the data in memory for performance and to support single-sign-on. Moving everything to an isolated enclave (Credential Guard) is the modern countermeasure, but many environments still lack it.

Connection

Every later technique is just a different way to get a privileged process (or a PPL process) to call the dump function on this particular target.

Active Recall – Explain it yourself

Click to reveal a good answer

LSASS holds the credential material of every interactive and network logon session that is still alive. Because the data must be available for authentication decisions, it sits in process memory in a form that can be parsed by tools such as Mimikatz once a dump is obtained. Therefore any technique that can force a MiniDump of LSASS (without necessarily crashing it) is high-value for credential access.

2. Windows Error Reporting – The Legitimate Photographer

Simple Explanation

Windows Error Reporting (WER) is the built-in system that notices when a program crashes, gathers diagnostic data (including a memory dump), and optionally sends a report to Microsoft. The main actors are the WER service (WerSvc) and two helper binaries: WerFault.exe (normal processes) and WerFaultSecure.exe (protected processes). Because these binaries are Microsoft-signed and run frequently, many security products treat their activity as low-risk.

Common Pitfall

Many detection rules simply exclude any process named WerFault.exe from LSASS-access alerts. That exclusion is exactly what the attacker is counting on. The correct approach is to allow-list expected WerFault behaviour (parent, command line, dump location) rather than the binary name alone.

3. Technique A – Silent Process Exit Abuse

Simple Explanation

Windows has a feature called Silent Process Exit. It lets an administrator say “when this process exits (even quietly), automatically create a dump.” Attackers configure that feature for LSASS and then call the undocumented API RtlReportSilentProcessExit on the LSASS process. The API tells WER “this process is exiting silently” without actually terminating LSASS. WerFault then creates the dump and the process continues running.

Key Steps
  1. 1
    Registry preparation
    Set IFEO GlobalFlag for lsass.exe to include the silent-exit monitor flag, and configure SilentProcessExit\lsass.exe with ReportingMode that includes LOCAL_DUMP and a DumpType of full memory.
  2. 2
    Obtain a suitable handle
    Open LSASS with rights that allow the silent-exit report (typically needs SeDebugPrivilege or equivalent).
  3. 3
    Call RtlReportSilentProcessExit
    This can be done from an external process or even injected into LSASS itself. The call does not kill the process.
  4. 4
    WerFault produces the dump
    A dump appears in the configured folder (often %TEMP%\Silent Process Exit or a LocalDumps path).
Why this is stealthy

No crash, no WerFault command line that looks exotic to a casual observer, and the dump is created by a process defenders already trust.

Detection pivot

Registry writes under Image File Execution Options\lsass.exe and SilentProcessExit\lsass.exe are rare in normal environments and highly suspicious.

4. Technique B – LSASS Shtinkering (ALPC/LPC Report)

Simple Explanation

Instead of using the Silent Process Exit registry path, this technique (presented at DEF CON 30 by Deep Instinct researchers) talks directly to the WER service over its internal LPC/ALPC port. The attacker crafts a message that says “an exception occurred inside LSASS” and supplies the necessary process and thread handles. WER believes the report, spawns WerFault, and a dump is written — again without LSASS actually crashing. The name “Shtinkering” comes from the Hebrew word for “snitching.”

Why it matters for purple teams

At the time of discovery the technique bypassed multiple commercial EDRs because their logic assumed that a dump generated by WerFault was always the result of a genuine crash. The attack forces a re-evaluation of that assumption.

Prerequisite often required: LocalDumps DumpType set to full (2) under HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps.
Common confusion

People mix this up with the Silent Process Exit technique. Both end with WerFault creating a dump, but the trigger mechanism is completely different (registry + RtlReportSilentProcessExit vs. direct LPC message to the service).

5. Technique C – WerFaultSecure + Old Binary (Modern Windows 11)

Simple Explanation

On modern Windows, LSASS is frequently protected by PPL. Ordinary processes cannot open it with the rights needed for a dump. However, WerFaultSecure.exe is itself a PPL process (WinTCB level) designed to dump other protected processes when they crash. Researchers discovered that the version of WerFaultSecure that shipped with Windows 8.1 still contains logic that can write an unencrypted dump. By bringing that older binary onto a Windows 11 machine and launching it under the correct PPL level (via CreateProcessAsPPL), an attacker can obtain a usable MiniDump of LSASS. The popular PoC tool WSASS automates the process and additionally renames the dump magic header to PNG so that simple signature-based scanners may ignore the file.

Purple-team implication

Monitor for WerFaultSecure.exe executing from non-System32 paths, large PNG files created by unusual parents, and the combination of CreateProcessAsPPL-style activity followed by a dump-sized file write.

6. Detection Engineering for Purple Teams

Simple Explanation

Because the dump is performed by a legitimate, signed binary, name-based allow-listing fails. Effective detection looks at the context: parent process, command-line arguments that reference the LSASS PID, unusual file paths for WerFaultSecure, large files with PNG extensions that contain MiniDump structures, and registry changes that enable full dumps or silent-exit monitoring for LSASS.

Purple-team testing mindset

Emulate each technique in an isolated lab, confirm the telemetry that appears, then verify whether your production detections fire. If they do not, the gap is a concrete finding you can hand to the blue team with a ready-made playbook.

Connections & Synthesis

All three techniques share the same end state: a MiniDump of LSASS written by a trusted Windows component. They differ only in the trigger:

  • Silent Process Exit – registry configuration + RtlReportSilentProcessExit
  • Shtinkering – direct LPC/ALPC message to the WER service
  • WerFaultSecure – bring an older PPL-capable binary and run it at WinTCB

Detection therefore cannot rely on “is this WerFault?” It must answer “is this WerFault activity expected given the parent, arguments, dump location, and surrounding registry changes?”

Modern mitigations (RunAsPPL, Credential Guard, ASR rules that block LSASS credential dumping) raise the cost of the classic methods, which is why the PPL-aware WerFaultSecure technique appeared. Purple teams should continuously re-evaluate coverage as both offensive and defensive capabilities evolve.

Key Takeaways

  • 1. WER is a legitimate dump factory; attackers just supply a false “crash” signal.
  • 2. Three main triggers: Silent Process Exit, direct LPC report, and old WerFaultSecure under PPL.
  • 3. Detection lives in context (parent, args, path, registry, file magic + size), not binary names.
  • 4. PPL and Credential Guard raise the bar; they do not eliminate the need for behavioural monitoring.
